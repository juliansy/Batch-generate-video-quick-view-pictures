# 02 · 流程审阅：不留情面的评判

> 历史记录：本文写于 v1 → v2 重写期间，里面的行数、默认值和流程描述只反映当时的状态。当前行为以仓库根目录的 README 与 [06-auto-grid.md](06-auto-grid.md)、[07-performance.md](07-performance.md) 为准。


审阅对象：`qvp.py` v1.1.0（76 行）与 [01-decomposition.md](01-decomposition.md) 里的流程。
证据来源：`probe-flow/` 下的五次实跑（该目录未随仓库发布，属本地实验记录）（Python 3.12.10 / moviepy 2.1.2 / Pillow 11.3.0 / Windows）。
结论先行：**这个脚本能跑，但不能交给别人跑。** 它把“发现文件、解码、标注、拼贴、落盘、报告”六件事塞进一个循环，任何一件出错就整批消失；成功与失败都只靠一行 print 表达，退出码不可判定。下面逐条列。

## 1. 缺陷清单

严重度：**阻断**（会毁掉一次批量任务）／**高**（结果不可信或无法运维）／**中**（特定输入下出错或明显浪费）／**低**（质量与整洁）。

## 2. 流程层面的根本问题

不是某一行写错，而是**流程形状**错了：

```text
发现 ──► 解码 ──► 标注 ──► 拼贴 ──► 落盘 ──► 报告
        └──────────── 一个 for 循环，共享一个异常域 ────────────┘
```

1. **没有阶段边界**：解码失败和落盘失败被同一种方式处理——整批退出。无法“这个视频跳过，继续下一个”。
2. **没有状态**：循环体里没有“当前文件处于哪个阶段”的概念，所以无法生成“哪个视频、哪一步、为什么失败”的报告。
3. **没有契约**：函数之间传的是 `list[PIL.Image]`，尺寸、数量、是否带时间戳全靠约定；格数与帧数不匹配这种错误没有任何一层能发现。
4. **没有可判定性**：成功=没抛异常。于是“丢了 4 帧”也算成功（F03）。
5. **纯计算与副作用混在一起**：取样时刻、时间格式、布局坐标埋在解码与粘贴里，测试只能整条链路跑。
6. **资源没有预算**：内存、像素总数、并发度都是“有多少吃多少”。

## 3. 新流程必须满足的不变量

| # | 不变量 | 对应缺陷 |
|---|---|---|
| I1 | 单个视频失败不影响其他视频；失败必须有可见信号 | F01 |
| I2 | 成功 = 产物通过校验（可打开、尺寸正确、格数正确）；不产出“看起来成功”的坏图 | F03, F04 |
| I3 | 覆盖必须是显式选择；默认不覆盖，跳过要说明 | F05, F27 |
| I4 | 输入文件永不修改、永不删除 | — |
| I5 | 报告可判定：每个文件的状态、原因、耗时；退出码与状态一致 | F10, F11, F13 |
| I6 | 内存有上限：超限时明确报错或降级，而不是把机器拖死 | F23 |
| I7 | 每个阶段可独立测试：纯函数不碰 I/O；I/O 阶段通过参数注入 | F15, F16, F17 |
| I8 | 采样必须覆盖全片，且不依赖“第一帧不是黑场”的运气 | F24 相关，见设计 |

## 4. 八维评分（v1.1.0）

| 维度 | 分数 | 一句话 |
|---|---|---|
| 健壮性 | 1/5 | 一个坏文件毁掉整批；帧数/格数不匹配静默丢数据 |
| 可靠性 | 2/5 | 能出图，但成功与失败的边界靠 print 表达 |
| 安全性 | 3/5 | 无注入面，也不删输入；但会静默覆盖输出 |
| 可理解性 | 3/5 | 76 行读得懂，但 `BORDER_SIZE` 与 `int()` 自相矛盾 |
| 可维护性 | 2/5 | 魔法数、职责混杂、无类型与文档 |
| 可测试性 | 1/5 | 没有可注入的边界，没有一行测试 |
| 可重用性 | 2/5 | 只能整体运行，无法作为库或处理任意目录 |
| 性能效率 | 2/5 | 200 MB 内存换一张 1.9 MB 的图；16 次 seek |

**总评 2.0/5**。这段代码是“一次成型的脚本”，不是“可以托付的工具”。下一步不是打补丁，而是按 [03-design.md](03-design.md) 重画流程。
