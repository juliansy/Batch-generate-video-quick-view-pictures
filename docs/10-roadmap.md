# 待办与已否决（Roadmap）

这个文件记录**不做的事**和**为什么**，避免同一个想法被反复重新想一遍。

## 不主动推进：全局内存闸门

**问题**：`-j 4` 同时渲染四张 4K 5x5 时，峰值内存约 4 × 2.2 GB；现在只有单张图的 `--max-pixels` 上限，没有跨任务的总量上限。审计把它列为唯一没被放过的高风险项。

**为什么先不做**：

- 现有 `--max-pixels` 已经挡住"单张就会爆"的输入；会出事的是"每张都不爆，但四张一起爆"，属于配置问题而非代码错误；
- 真实使用里 `-j` 默认 1，出问题的前提是用户主动把 `-j` 调大又同时喂 4K 素材；
- 做一个可靠的闸门需要跨平台读取可用内存（Windows `GlobalMemoryStatusEx`、POSIX `sysconf`），并决定"拒绝、降档还是排队"，这些策略比代码本身更难，仓促实现只会制造新的误报。

**真要做的形状**（留给出问题那天）：

```text
估算 = Σ(画布像素 × 11 B) + 进程自身开销
if 估算 > 可用内存 × 0.6:
    默认拒绝，写清"降低 -j 或用 --max-pixels"
    --force-memory 可越过
```

触发条件：有人报告内存耗尽，或 `-j` 的并行渲染成为常规用法。

## 已否决：远程 seek 取帧（2026-11）

想法：把视频直链交给 ffmpeg，用 `-ss` 在 HTTP 层 seek，只取需要的帧，不下载整片。

实测否决（120 s / 1920×1080 / 20 帧，统计服务器实际写出字节）：

| 做法 | 传输量 |
|---|---|
| 20 次分散 seek | 342 MB（2.0× 文件） |
| 20 次关键帧 seek | 350 MB（2.1×） |
| 单遍下载后本地取帧 | 171 MB（1.00×） |
| 20 个关键帧的压缩载荷（理论下限） | 1.33 MB |

原因：每个 ffmpeg 进程开场都要读一次 `bytes=0-`（实测 2.75 MB 探测），随后是一次开口 Range 的 GOP 读取（4–8 MB）；关键帧只消掉"从关键帧往前解码"这一小段。要摸到 1.33 MB 得自己解析 mp4/DASH 索引、按字节区间取 sample，是另一个量级的工程。

结论：**下载再本地处理**在任何帧数下都不亏，且可预测。线上视频能力若要做，正确形状是"下载最低档 → 走本地流程 → 删临时文件"。

## 已实现：aria2 RPC 联动（v2.10.0）

Bilibili-Evolved 的 `aria2-output` 插件通过 `aria2.addUri` 把视频/音频/字幕分片投给 aria2，文件落在 aria2 的 `dir` 下，名字来自 `out` 参数（标题）。

可能的接法：`qvp.py --aria2 http://127.0.0.1:6800/jsonrpc` 查询 `aria2.tellStopped`，拿 `files[].path` 直接处理，跳过目录扫描。好处是与插件解耦（任何 aria2 客户端都适用），代价是依赖用户开着 aria2 的 RPC 端口。

落地形状：拉取式 `--aria2`（查 `tellStopped`，只取视频文件）与推送式 `--aria2-hook`（aria2 的 `--on-download-complete` 追加 gid，脚本据此查 `tellStatus`）。测试用本地假 RPC 服务器覆盖了过滤、去重、密钥、gid 与不可达五种情况。
