# 04 · v2 代码质量评审

> 历史记录：本文写于 v1 → v2 重写期间，里面的行数、默认值和流程描述只反映当时的状态。当前行为以仓库根目录的 README 与 [06-auto-grid.md](06-auto-grid.md)、[07-performance.md](07-performance.md) 为准。


对象：`qvp.py` v2.0.0（768 行 / 28,083 字节）与 `tests/test_qvp.py`（374 行 / 38 用例）。
方法：逐段读代码 + 跑用例 + 真实素材实测 + 独立子代理对抗式评审 + 内存采样。
评分 1–5 分，5 为“可以交给陌生人维护”。

## 1. 总览

| 维度 | v1.1.0 | v2.0.0 | 一句话理由 |
|---|---|---|---|
| 健壮性 | 1 | **4** | 坏文件不再毁整批；预算/格数/字体/输出冲突都有明确失败；扣分项是“文件中途损坏”仍导致该文件整体失败 |
| 可靠性 | 2 | **4.5** | 状态机只有 ok/skipped/failed/planned，退出码由它派生；产物必须通过重新打开校验才替换 |
| 安全性 | 3 | **4** | 不碰输入、不拼 shell、覆盖必须显式；扣分项是输出目录若为符号链接不校验 |
| 可理解性 | 3 | **4** | 文件顶部有分层说明，纯函数在前、I/O 在后；扣分项是单文件 768 行、界面为英文 |
| 可维护性 | 2 | **4** | 数据结构化（Probe/Layout/Job/Result）+ 无全局可变状态；扣分项是 `render_job` 仍偏长 |
| 可测试性 | 1 | **5** | 纯逻辑与 I/O 分离，`main(argv)` 可注入，38 个用例含真实 ffmpeg |
| 可重用性 | 2 | **3.5** | 可作为模块 import；扣分项是没有库级配置对象、入口仍是单文件 |
| 性能效率 | 2 | **4.5** | 同一批素材 19.8 s → 8.0 s；扣分项是每帧一次进程、内存受画布支配 |

综合：**2.0 → 4.2**。

## 2. 逐维发现

### 2.1 健壮性

| # | 严重度 | 发现 | 证据 | 处理 |
|---|---|---|---|---|
| C01 | 高 | 0.3 秒 / 10 fps 的视频，最后一个采样点 0.25 s 已经越过末帧，`ffmpeg` 返回 0 字节，整个文件被判失败 | 新增用例 `test_very_short_video_still_renders` 第一次跑就红 | 采样按帧率回退 1.5 帧；`frame_source` 对非首帧失败再回退 2 帧重取；用例转绿 |
| C02 | 高 | 采样从 0 秒开始（v1 做法）会把片头黑场放进第一格；改中心采样后又丢掉片头 | 长视频第一格对比 | 改成“端点包含 + 内缩”：第一格在 0.5 s（短片取 1%），最后一格停在结束前 1.5 帧 |
| C03 | 中 | 单帧解码失败（中间损坏）仍会让整个文件失败 | 代码路径 `FrameError` → `finish_failure` | 保留该行为并写进文档：宁可整张不产出，也不产出缺格的图；回退重取已覆盖“末帧越界”这一类 |
| C04 | 中 | `--max-pixels` 只拦画布，不拦“解码后单帧内存” | 代码：预算基于 layout | 单帧内存由 ffmpeg 管道 + PIL 各一份，量级与画布同阶；已在文档写明 4K 约 1.1 GB |
| C05 | 低 | Ctrl-C 会留下 `.tmp-<pid>` 文件 | 代码审查：`except Exception` 不捕 `KeyboardInterrupt` | `finally` 里 `tmp.unlink(missing_ok=True)`，成功路径是 no-op |

## 3. 对抗式评审（独立子代理）

让一个独立评审代理在不看作者结论的前提下通读代码与 38 个用例，只找“会在真实文件上炸”的问题。它交出 6 条高危、5 条中危、13 条低危，以及 11 条测试缺口。**逐条核对后全部成立**，其中最狠的三条是我自己没抓到的：

| # | 级别 | 问题 | 处理 |
|---|---|---|---|
| H1 | 高 | `--grid 4x4x4` 抛 `UsageError` 逃出 `main()`：argparse 只认 `ArgumentTypeError/TypeError/ValueError`，于是变成 traceback + 退出码 1，而文档承诺 2 | `grid_arg()` 适配层；`main` 捕获 `SystemExit` 返回其 code。新增用例断言 `== 2` 且无 Traceback |

它同时确认了一批**做对了**的地方，避免过度改动：网格几何、原子写、跳过/覆盖语义、串行与并发下的失败隔离、输入只读、无命令注入、旋转元数据（moviepy 2.1.2 会交换宽高，ffmpeg 也自动旋转）、时间码进位、参数范围、预算在分配前检查、排序与去重、`--log` 追加语义。

它的三条“不确定、未复现”原样保留在风险清单里（见下一节第 4、5 条）。

## 4. 仍未解决的风险

1. **单文件 768 行**：为了“下载一个文件就能跑”，没有拆包。缓解手段是文件内分层 + 纯函数。若将来加功能，优先考虑 `qvp/` 包 + 单文件 zipapp，而不是继续加长。
2. **每帧一次 ffmpeg 进程**：长视频（1 小时）16 次 seek 仍是 2–3 秒级；一次解码多处取样能把启动开销摊掉，但会引入“整片解码”的时长风险，暂不做。
3. **内存上限靠人工**：4K × 4×4 就是 1.1 GB，`--max-pixels` 只是闸门不是解法；真正的解法是降采样，未实现。
4. **旋转元数据**：手机竖拍视频若 probe 尺寸与解码尺寸不一致，ffmpeg 路径会失败并回退 moviepy（自动兜底），但没有真实素材验证。
5. **未测**：磁盘写满、目标被占用（Windows 文件锁）、`--jobs` 下多个文件同时失败。
6. **界面语言**：控制台与错误信息是英文，README 双语。这是刻意选择（`Processing…` 是既有行为），但中文用户读错误信息需要一点英文。

## 5. 结论

v2 的改进不在“代码更漂亮”，而在**失败被变成了数据**：每个文件都有状态和原因，退出码可判定，产物必须过校验，输入永不改动。这四条是这次重构真正的产出；性能与内存只是副产品，其中内存那条还是负面的，已经如实记录。
