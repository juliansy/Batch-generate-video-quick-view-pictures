# 07 · 性能：怎么测的、热点在哪、改了什么

## 1. 工具

没有自己造轮子，用的都是标准件：

| 工具 | 用途 | 结论来源 |
|---|---|---|
| `cProfile` + `pstats` | Python 层函数耗时（`tottime` / `cumtime`） | 确认 Python 侧几乎没有耗时，大头在 `subprocess` 等待 |
| 分段计时（monkeypatch `probe_video`、`grab_frame_ffmpeg`、`Image.save`） | 把一次渲染拆成 探测 / 解码 / 描边 / 拼贴 / 编码 | 解码占 92–94% |
| `ThreadPoolExecutor` 微基准 | 并行解码的 worker × threads 组合 | 4 进程最优（线程数交给 ffmpeg） |
| `python -X importtime` | 冷启动导入耗时 | PIL ~110 ms，moviepy 已改为懒加载 |
| `time.perf_counter` / 行级时间戳包装器 | 首行输出延迟、阶段墙钟 | 0.13 s 出横幅 |

没有用到的：`py-spy`、`scalene`、`memray`、`line_profiler`（都能装，但这几项结论用内置工具已经足够；py-spy 适合“不知道慢在哪”的采样，这里一开始就知道嫌疑在子进程）。

测量脚本已随仓库提供：`tools/bench_profile.py`（分段 + cProfile）、`tools/bench_decode.py`（串行 vs 并行，自动建临时目录）。

## 2. 单次渲染的阶段成本（v2.2，4K AV1 515 秒 / 5×5 / 25 帧）

```
decode   7.7 s  (94%)   ← 25 次 ffmpeg，每次 seek 到关键帧再解码到目标时刻
save     0.35 s (4%)    ← 208 MP 画布编码 JPEG（v2.3 时的设置；v2.9 起改 q82/4:4:4/渐进式，166 MP 约 1.7 s）
fill     0.43 s (5%)    ← Image.new 白底
paste    0.07 s
probe    0.07 s
stamp    0.03 s
```

cProfile 的 `tottime` 前三名是 `BufferedReader.read`（12.7 s，读 ffmpeg 的 rawvideo 输出）、`PIL._imaging.fill`、`ImagingEncoder.encode_to_file`——也就是说 **Python 代码本身不是瓶颈，瓶颈是“一次 ffmpeg 只取一帧”的解码方式**。

原因：`-ss` 在输入前是快速 seek，ffmpeg 跳到目标前最近的关键帧，然后**解码到目标时刻**。4K VP9/AV1 的 GOP 常有 100–240 帧，取 1 帧的代价接近解码好几秒的画面。

## 3. 优化一：并行取帧（v2.3）

单个 ffmpeg 进程已经会用多线程解码（`-threads 1` 反而慢 2 倍），所以并行的收益来自**重叠多个 seek+解码**，而不是把一帧拆开。实测组合（16 核 / 4K VP9 121 秒 / 12 帧）：

| workers | threads/进程 | 12 帧耗时 | 每帧 |
|---|---|---|---|
| 1 | 自动 | 12.94 s | 1078 ms |
| 2 | 8 | 8.51 s | 709 ms |
| 3 | 5 | 7.65 s | 637 ms |
| 4 | 4 | 7.57 s | 631 ms |
| 6 | 3 | 7.46 s | 621 ms |

规则：`workers = min(4, cpu/4, 帧数)`，`threads = 0`（交给 ffmpeg 自己决定；v2.9 实测把每进程线程限到 cpu/workers 反而从 13 s 慢到 19 s），默认开启，`--decode-workers N` 可覆盖（1 = 退回串行）。取帧线程池保持“领先合成器 workers+1 帧”的窗口，内存只多几帧（4K 每帧 25 MB）。

端到端（v2.2 串行 → v2.3 默认）：

| 素材 | 网格/帧数 | 改前 | 改后 | 加速 |
|---|---|---|---|---|
| 4K VP9 121 s | 4×3 / 12 | 14.19 s | 9.36 s | 1.52× |
| 4K AV1 515 s | 5×5 / 25 | 11.99 s | 9.06 s | 1.32× |
| 1080p AV1 384 s | 5×4 / 20 | 3.86 s | 2.95 s | 1.31× |
| 1080p H.264 436 s | 5×4 / 20 | 3.49 s | 1.55 s | 2.25× |

## 4. 优化二：去掉每帧一次全尺寸拷贝

原来每帧先 `ImageOps.expand(image, border)` 造一张“带白边的整帧”，再贴到画布。白边本来就是白画布的底色，所以改成**按偏移直接贴**：省掉一次 25 MB 的分配与拷贝，4K 下每帧约 18 ms，25 帧约 0.45 s。

## 5. 优化三（v2.2 已做）：探测换 ffprobe

`moviepy.VideoFileClip` 打开一个 4K 文件要 1019 ms，ffprobe 读 JSON 只要 70 ms；30 个视频的计划阶段从 15.8 s 降到 2.3 s。

## 5.5 GPU 解码：一组参考测量

下面的数字来自一次测试：Windows 11、Ryzen 7 5800U、RTX 3050 Laptop 4 GB、ffmpeg 8.x（NVDEC）。换显卡、驱动或 ffmpeg 构建，结果会不同，所以只当作参考，不要当结论。

测试素材用字母代称（避免暴露具体片源）：A–H 为 4K，时长 100–450 秒。

### 5.5.1 每帧一个 ffmpeg 进程

| 片段 | 编码 | 软件 | `--cuda` |
|---|---|---|---|
| A 450 s | VP9 | 6.04 | 10.38 |
| B 300 s | AV1 | 6.43 | 6.66 |
| C 265 s | AV1 | 2.84 | 4.17 |
| D 214 s | AV1 | 5.90 | 5.83 |
| E 210 s | H.264 | 6.03 | 10.30 |
| F 207 s | VP9 | 4.69 | 6.08 |
| G 198 s | VP9 | 6.42 | 7.94 |
| H 100 s | AV1 | 11.30 | 7.93 |

8 个里 6 个更慢。原因是形状：每帧一个进程就要付一次 CUDA 上下文初始化（约 250 ms），1080p 一帧在 CPU 上只要 150 ms。

### 5.5.2 一个进程带多个 seek（`--batch-seek`）

每个输入都要重复 `-hwaccel cuda -hwaccel_output_format cuda`；漏了这一点，第二个输入会退回软件解码——早期的一次批量测试就是这样误判的。

| 片段 | 编码 | 软件 | `--cuda` | 批量 CPU | 批量 `--cuda` |
|---|---|---|---|---|---|
| A | VP9 | 6.04 | 10.38 | 4.33 | **3.98** |
| B | AV1 | 6.43 | 6.66 | 6.20 | **4.55** |
| C | AV1 | 2.84 | 4.17 | 2.35 | **2.07** |
| D | AV1 | 5.90 | 5.83 | 5.60 | **3.24** |
| E | H.264 | 6.03 | 10.30 | **4.65** | 7.98 |
| F | VP9 | 4.69 | 6.08 | 3.17 | **3.07** |
| G | VP9 | 6.42 | 7.94 | 5.55 | **4.91** |
| H | AV1 | 11.30 | 7.93 | 11.89 | **5.28** |

批量后 GPU 在 7/8 个片段上最快；批量对 CPU 也有效（摊薄解码器启动与 demux）。H.264 的 4K 素材是例外，CUVID 反而慢 1.7×。

### 5.5.3 观察到的现象

- **GPU 利用率 9–47%**（多数 15–22%）：瓶颈在把任务喂给解码器的方式（seek、demux、下载帧的串行段），不在 NVDEC 吞吐。
- **显存**：8 个输入/进程时峰值约 2.6–3.5 GB；4 GB 卡上 12 个输入也能跑通但已接近上限，所以 `--cuda` 默认 `--batch-seek 4`、并发 2。

### 5.5.4 端到端

`--cuda --batch-seek 4` 对 4K：

| 片段 | 编码 | 软件 | `--cuda` |
|---|---|---|---|
| D | AV1 | 13.72 s | 8.74 s |
| H | AV1 | 17.46 s | 10.45 s |
| A | VP9 | 9.83 s | 9.72 s |
| F | VP9 | 8.65 s | 8.26 s |
| E | H.264 | 12.45 s | 13.38 s |

### 5.5.5 未验证项

- 驱动版本与 CUDA 运行时的组合；
- 竖屏 10-bit VP9 的 NVDEC 路径；
- 更好的喂法（一次解码一段关键帧区间、复用解码器）；
- 样本量：一台机器、8 个片段。

## 6. 被否掉的方案

| 方案 | 为什么不采用 |
|---|---|
| 硬件解码（CUDA / D3D11 / QSV） | 结果依赖显卡与驱动，脚本的目标是“拷给谁都能跑”；同一份产物在软/硬解下可能有细微差异。**另外一次并发基准把显卡跑满，导致正在运行的桌面端被系统以 OOM 杀掉——这是我的测试方法有问题，不是脚本的问题，之后所有基准都只用 CPU、串行起子进程、输出到 NUL。** 需要的话可以自己加 `--ffmpeg-args`。 |
| `-threads 1` 给每个进程 | 单帧耗时翻倍（1078 → 1851 ms） |
| `-probesize 32k -analyzeduration 0` | 反而更慢（+8%），seek 前的探测不是瓶颈 |
| 一次 ffmpeg 用 `select` 滤镜取全部帧 | 要从头解码整个文件；4K 515 秒素材约 60 s+，远慢于 25 次 seek |
| numpy 拼画布 | 仍要一次 300–600 MB 的拷贝；Pillow 的 `paste` 已经在这条路径上 |

## 7. 剩下的大头

- **解码仍是 90%+**：这是“精确到秒地从任意位置取一帧”的固有成本。要再快只能牺牲精度（取关键帧）或依赖硬件，两样都不做默认。
- JPEG 编码 208 MP 约 0.35 s（v2.3 设置）、白底分配 0.43 s，合计 <10%，不值得为它们增加复杂度。v2.9 换成 4:4:4 + 渐进式后编码升到约 1.7 s/166 MP，仍远小于解码，换来时间码不糊。
- 内存：4K 5×5 画布 624 MB，加上并行解码的几帧，峰值约 2.2 GB（约 11 字节/像素，实测）。8 GB 机器上建议 `--decode-workers 1` 或 `--max-pixels` 限一档。

## 8. 复现

```text
python tools/bench_profile.py "D:\Videos\clip.mp4"      # 分段 + cProfile + 热点
python tools/bench_decode.py "D:\Videos\a.mp4" "D:\Videos\b.mp4"   # 串行 vs 并行
python qvp.py -V                                         # 版本
python -m unittest discover -s tests                     # 117 个用例
```

基准只用 CPU、一次只起一个基准进程、ffmpeg 输出到 `NUL`；不要在这些基准里加硬件解码参数——那会和其他使用 GPU 的程序抢显存。
